# The measured frontier: 5/6 reached, and PP vs KLD is provably exclusive

Supersedes the earlier draft of this file, which treated all-FP6 as the only
fidelity option and therefore understated what is reachable. Every number is
measured on the current stack (V2 runner + zero-depth fixes + mnbt 3072 +
util 0.93 + int6 embeds); PP/TG rows are the Phase-0 harness at **n=3 boots**.

(~0.0007) rather than any GEMM approximation.

## Why criterion 1 and criterion 3 cannot both hold on 31.4 GiB

Proven from both directions, with measurements:

**From the FP4 side.** Resident FP4-class weights give PP 7666, but the
validated additive model (`receipts/kld-axis-conclusion-2026-08-19.md`,
held-out prediction accurate to 1.1%) leaves a post-floor budget of 0.00732,
and the *smallest single FP4 group* (`down_proj`, 0.0127) alone exceeds it. No
FP4 subset assignment reaches 0.012. all-FP6 does reach it (0.0107) but costs
5.03 GiB of weights, which caps context at a measured **99,552** and drops PP to
4648.

**From the trellis side.** Trellis weights reach KLD 0.003412 but must be
decoded per prefill chunk, so PP is 1081. The bake-off
(`tools/kernel-bakeoff.py`) bounds every decode-per-chunk variant at M=2051:

| path | ms/chunk | implied PP |
|---|---|---|
| fused `exl3_gemm` (measured in production) | — | **1081** |
| fp8dg, fused reconstruct+UE8M0 (est.) | 693 | **2958** |
| fp8dg, cached weights | 220 | 9301 |
| FP4, resident | 165 | 12452 |

Even a *perfect* fused `reconstruct -> UE8M0-FP8` kernel — the objective's
headline item — tops out near **2958 tok/s** on the 2051-token benchmark,
because the weight decode is paid once per chunk and a 2051-token prompt is one
chunk. (Its predicted 6-9k assumed 8192-token chunks; at M=8192 the same
estimate is 6209, but the benchmark prompt cannot fill that.) Reaching 7000
requires the decode *not* to happen per chunk, i.e. GEMM-ready weights resident:
FP8 for all 24.3e9 quantized params is 22.6 GiB, which cannot coexist with a
238,400-token KV cache in 31.4 GiB.

So the deadlock is memory, not kernel quality: **trellis-grade fidelity in a
GEMM-resident format does not fit.** That also means W4A8 (b12x #232) would help
KLD only partially — FP4 E2M1 weights are a crude grid next to the trellis
lattice, so W4A8 plausibly lands ~0.02-0.03, still above 0.012.

## Recommendation

Both profiles are one env-var group apart and both are recorded here, so either
is a known path back:

- **all-FP4 (default today)** — general serving. Only profile with PP >= 7000.
- **all-trellis** — fidelity/chat serving: 5/6 criteria, KLD 0.0034, TG 207.6
  fox / 92.9 essay, full 238,400 context. Prefill-heavy workloads pay 7x.

Awaiting the human's call on which should be the shipped default, since the
choice trades a 7x prefill regression against a 16.6x fidelity gain and cannot
be resolved from the objective alone.
