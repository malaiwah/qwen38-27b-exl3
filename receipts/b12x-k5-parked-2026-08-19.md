# PARKED: routing K5 through B12X is +51% PP but corrupts the model — and B12X is not at fault

**Date:** 2026-08-19
**Status:** parked at the objective's 3-attempts-per-hypothesis cap, with the bug
localised to *our* integration and B12X exonerated by measurement.
**Default:** `VLLM_EXL3_B12X_ANY_BITS` stays `0`. Setting it to `1` now logs a
loud one-shot warning naming this receipt.

## The prize

After B12X was enabled for the K6 matrices (`receipts/b12x-shared-scratch-2026-08-19.md`,
PP 1080.6 → 1630.0), the K5 matrices — `mlp.gate_proj`/`up_proj`, **6.64 GiB and
the largest matrices in the model** — were still falling back to the fused
`exl3_gemm` reconstruct+fold path at 4.72 ms CPU per call. `_b12x_trellis_k6_supported`
gates on `n_words == 96` (K6) by default; `VLLM_EXL3_B12X_ANY_BITS=1` admits
48/64/80/96.

Turning it on:

| | K6-only b12x | + K5 via b12x |
|---|---|---|
| PP, 2051-tok | 1630.0 ± 3.6 | **2457.7** (2442-2461 over 6 reps) |
| sanity completion | "Paris." | **`'Fonilet豁知己uty'`** |
| TG fox | 210.2 | 23.8 |
| MTP acceptance | 0.281 | **0.000** |
| vision | pass | **fail** |

So it is a further **+50.8% prefill** — and the model is destroyed. Coherent
throughput numbers with incoherent output: exactly the failure mode the
objective's kernel-correctness rule exists to catch. Nothing raised; it just
produced wrong numbers.

## B12X's bits=5 dense GEMM is correct in isolation

Before blaming B12X, it was measured directly on **real checkpoint weights** —
`tools/b12x-k5-selftest.py`, layer 3, comparing B12X `prepare_weight` + `run`
against `exllamav3_ext.reconstruct` + `hadamard_fold_weight_chunked` (the
bit-faithful reference the served model agreed with before B12X):

| matrix | bits | shape | cos | max_rel | verdict |
|---|---|---|---|---|---|
| `down_proj` (control) | 6 | 17408×5120 | 1.000000 | 8.38e-04 | ok |
| **`gate_proj` (subject)** | **5** | **5120×17408** | **1.000000** | **9.54e-04** | **ok** |

The K5 error is the same magnitude as the K6 control that is currently serving at
KLD 0.003407. Passing the checkpoint's own `mcg` tensor explicitly (rather than
only `codebook="mcg"`, which is what the integration does) changes nothing —
identical to 6 digits — so the codebook argument is not under-specified either.

**Conclusion: the bits=5 kernel is fine. The corruption is in this integration.**
Filing a bug against B12X would have been wrong, which is why the isolation was
run first.

## What was ruled out

- **Bits inference:** B12X derives bits from the payload
  (`_trellis256_bits_from_native_tensor`), and `prepare_trellis256_dense_weight`
  validates K/N divisibility by 128; K5 is accepted, not silently mis-strided.
  `prepare.py:1575` allows bits ∈ (3,4,5,6).
- **`mcg` argument:** see above, no effect.
- **dtype:** B12X rejects a non-fp16 `rotated_f16` with a hard `ValueError`
  ("rotated_f16 must be contiguous, 16-byte-aligned torch.float16"), so a bf16
  mismatch cannot corrupt silently — it cannot run at all. The served model is
  fp16 on this path.
- **Scratch sizing:** the shared accumulator is sized at the maximum over every
  allowed block size *including* the `moe_block_size == 8` doubling, so it is not
  under-allocated for K5.

## Leading remaining suspects (for whoever picks this up)

1. **Merged linears.** `mlp.gate_up_proj` is a `MergedColumnParallelLinear`;
   `apply` runs per shard and `torch.cat`s. Every K6 matrix that works is either
   unmerged or the 3-way `qkv_proj`, so the *interaction* of K5 with per-shard
   dispatch is untested. If a shard is handed a non-contiguous view along dim 1,
   B12X's validation may accept strides it then ignores.
2. **Prepared-weight cache identity.** `_b12x_trellis_weight` keys on
   `(id(suh), id(svh), dtype)` stored on the trellis tensor. `id()` is reused
   after garbage collection; two shards whose scale tensors were freed and
   reallocated could collide and be served the wrong prepared weight — which
   would produce exactly this "plausible shapes, wrong values" corruption.
3. **N window.** `VLLM_EXL3_B12X_N_RANGE` defaults to `5120-32768`; the merged
   `gate_up` is N=34816 (outside) while each shard is 17408 (inside), so the
   route can differ between the fused and per-shard views of the same weight.

Suspect 2 is the cheapest to eliminate (key on `data_ptr()` plus shape, or hang
the cache off the module) and is the one I would try first.

## Why it is parked rather than pursued

The objective caps a single hypothesis at 3 attempts (spent: serving A/B, fp16
isolation, bf16 isolation) and the upside does not change the outcome of the
north star: 2457.7 is still **2.8× short** of criterion 1's 7000 tok/s, on a
profile that already satisfies criteria 2-6. It is a real +51% for prefill-heavy
fidelity workloads, so it is worth finishing later — but it is not on the
critical path, and shipping it would trade a working model for a fast one.

## Guard added

`_b12x_trellis_k6_supported` now emits a one-shot `logger.warning` when
`VLLM_EXL3_B12X_ANY_BITS=1`, stating that the path is known-broken end-to-end,
that B12X itself is correct in isolation, and pointing here. The variable is
attractive (+51% PP) and its failure is silent, so an unguarded env flag was a
trap. `EXL3_PATCH_SHA256` re-pinned to `0b9889b02d...`.
