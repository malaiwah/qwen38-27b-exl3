# PARKED: routing K5 through B12X is +51% PP but corrupts the model — and B12X is not at fault

**Date:** 2026-08-19
**Status:** parked at the objective's 3-attempts-per-hypothesis cap, with the bug
localised to *our* integration and B12X exonerated by measurement.
**Default:** `VLLM_EXL3_B12X_ANY_BITS` stays `0`. Setting it to `1` now logs a
loud one-shot warning naming this receipt.

## The prize

After B12X was enabled for the K6 matrices (`receipts/b12x-shared-scratch-2026-08-19.md`,
PP 1080.6 → 1630.0), the K5 matrices — `mlp.gate_proj`/`up_proj`, **6.64 GiB and
the largest matrices in the model** — were still falling back to the fused
`exl3_gemm` reconstruct+fold path at 4.72 ms CPU per call. `_b12x_trellis_k6_supported`
gates on `n_words == 96` (K6) by default; `VLLM_EXL3_B12X_ANY_BITS=1` admits
48/64/80/96.

Turning it on:

| | K6-only b12x | + K5 via b12x |
|---|---|---|
| PP, 2051-tok | 1630.0 ± 3.6 | **2457.7** (2442-2461 over 6 reps) |
| sanity completion | "Paris." | **`'Fonilet豁知己uty'`** |
| TG fox | 210.2 | 23.8 |
| MTP acceptance | 0.281 | **0.000** |
| vision | pass | **fail** |

So it is a further **+50.8% prefill** — and the model is destroyed. Coherent
throughput numbers with incoherent output: exactly the failure mode the
objective's kernel-correctness rule exists to catch. Nothing raised; it just
produced wrong numbers.

## B12X's bits=5 dense GEMM is correct in isolation

Before blaming B12X, it was measured directly on **real checkpoint weights** —
`tools/b12x-k5-selftest.py`, layer 3, comparing B12X `prepare_weight` + `run`
against `exllamav3_ext.reconstruct` + `hadamard_fold_weight_chunked` (the
bit-faithful reference the served model agreed with before B12X):

| matrix | bits | shape | cos | max_rel | verdict |
|---|---|---|---|---|---|
| `down_proj` (control) | 6 | 17408×5120 | 1.000000 | 8.38e-04 | ok |
| **`gate_proj` (subject)** | **5** | **5120×17408** | **1.000000** | **9.54e-04** | **ok** |

The K5 error is the same magnitude as the K6 control that is currently serving at
KLD 0.003407. Passing the checkpoint's own `mcg` tensor explicitly (rather than
only `codebook="mcg"`, which is what the integration does) changes nothing —
identical to 6 digits — so the codebook argument is not under-specified either.

**Conclusion: the bits=5 kernel is fine. The corruption is in this integration.**
Filing a bug against B12X would have been wrong, which is why the isolation was
run first.

## What was ruled out

- **Bits inference:** B12X derives bits from the payload
  (`_trellis256_bits_from_native_tensor`), and `prepare_trellis256_dense_weight`
  validates K/N divisibility by 128; K5 is accepted, not silently mis-strided.
  `prepare.py:1575` allows bits ∈ (3,4,5,6).
- **`mcg` argument:** see above, no effect.
- **dtype:** B12X rejects a non-fp16 `rotated_f16` with a hard `ValueError`
  ("rotated_f16 must be contiguous, 16-byte-aligned torch.float16"), so a bf16
  mismatch cannot corrupt silently — it cannot run at all. The served model is
  fp16 on this path.
- **Scratch sizing:** the shared accumulator is sized at the maximum over every
  allowed block size *including* the `moe_block_size == 8` doubling, so it is not
  under-allocated for K5.

## Leading remaining suspects (for whoever picks this up)

1. **Merged linears.** `mlp.gate_up_proj` is a `MergedColumnParallelLinear`;
   `apply` runs per shard and `torch.cat`s. Every K6 matrix that works is either
   unmerged or the 3-way `qkv_proj`, so the *interaction* of K5 with per-shard
   dispatch is untested. If a shard is handed a non-contiguous view along dim 1,
   B12X's validation may accept strides it then ignores.
2. ~~**Prepared-weight cache identity.**~~ **Checked and largely exonerated.**
   `_b12x_trellis_weight` keys on `(id(suh), id(svh), dtype)`, and `id()` reuse
   after GC would indeed serve the wrong prepared weight. But the scale tensors
   are per-shard entries in `layer.suh.exl3_tensors[shard_id]` — model parameters
   that outlive the cache — and the cache itself hangs off the matching
   per-shard trellis tensor. So a cached entry cannot outlive its key's tensor,
   and the aliasing window does not open. Recorded here because I listed it as
   the first thing I would try; it is not that.
3. **N window.** `VLLM_EXL3_B12X_N_RANGE` defaults to `5120-32768`; the merged
   `gate_up` is N=34816 (outside) while each shard is 17408 (inside), so the
   route can differ between the fused and per-shard views of the same weight.

With suspect 2 eliminated, **suspect 1 (merged-linear per-shard dispatch) is the
one to try first**: it is the only structural difference between the K5 matrices
and the K6 matrices that demonstrably work, and `tools/b12x-k5-selftest.py`
already provides the reference harness — extend it to feed B12X the *shard view*
that `apply` passes, rather than a standalone tensor, and the disagreement should
reproduce outside the server.

## Why it is parked rather than pursued

The objective caps a single hypothesis at 3 attempts (spent: serving A/B, fp16
isolation, bf16 isolation) and the upside does not change the outcome of the
north star: 2457.7 is still **2.8× short** of criterion 1's 7000 tok/s, on a
profile that already satisfies criteria 2-6. It is a real +51% for prefill-heavy
fidelity workloads, so it is worth finishing later — but it is not on the
critical path, and shipping it would trade a working model for a fast one.

## Guard added

`_b12x_trellis_k6_supported` now emits a one-shot `logger.warning` when
`VLLM_EXL3_B12X_ANY_BITS=1`, stating that the path is known-broken end-to-end,
that B12X itself is correct in isolation, and pointing here. The variable is
attractive (+51% PP) and its failure is silent, so an unguarded env flag was a
trap. `EXL3_PATCH_SHA256` re-pinned to `0b9889b02d...`.

## SECOND PASS (same day): the GEMM is exonerated at every bitrate and row count

Three further hypotheses were tested and refuted, which took this work item to
the objective's **6-attempt halt cap**. All three were worth running because each
would have been a different fix (and one would have been an upstream bug).

### New instrumentation: `VLLM_EXL3_B12X_SELFTEST=1`

The standalone harness compares *checkpoint* tensors, which cannot see padding,
merged-shard views, or loader transforms. So the objective's required check was
added to the serving path itself: a one-shot, per-`(prefix, shard, m, K, Npacked,
n_words)` comparison of `_b12x_trellis_linear` against `_exl3_gemm` on **the real
served tensors**, logging cos/max_rel and serving the reference on that call.
Now forwarded by the launcher (it was silently dropped at first — the container
only receives explicitly listed `-e` vars, so the flag appeared to do nothing).

Two bugs in the first version of the check, both fixed, both worth recording:

1. **Zero-input false alarms.** 369 of 374 lines reported `cos=0.000000
   max_rel=0`, which looks catastrophic and means nothing: vLLM's memory-profiling
   dummy runs feed all-zero activations, so *both* outputs are zero and cosine
   similarity is 0/0. Guarded with `x.abs().amax() > 0`, mirroring the existing
   FP8DG selftest.
2. **Decode was never tested.** The key omitted `m`, so the first (prefill) call
   consumed the key and every decode shape went unchecked — while the garbage is
   produced *by decode*. `m` is now part of the key, because b12x takes different
   kernels for small vs large M.

### Result: every route agrees

| bits | m | K | Npacked | cos | max_rel |
|---|---|---|---|---|---|
| 4 | 3072 | 10240 | 5120 | 1.000000 | 1.23e-04 |
| 4 | 4 | 10240 | 5120 | 0.999999 | 3.47e-04 |
| 5 | 3072 | 5120 | 17408 | 1.000000 | 5.69e-04 |
| 5 | 3072 | 5120 | 17408 | 1.000000 | 9.59e-04 |
| **5** | **4** | 5120 | 17408 | **0.999999** | 1.13e-03 |
| **5** | **4** | 5120 | 17408 | **0.999999** | 1.14e-03 |
| 6 | 3072 | 17408 | 5120 | 0.999999 | 2.42e-04 |
| 6 | 3072 | 5120 | 12288 | 1.000000 | 8.87e-04 |
| 6 | 4 | 17408 | 5120 | 0.999999 | 4.62e-04 |
| 6 | 4 | 5120 | 12288 | 1.000000 | 1.10e-03 |

**0 mismatches on nonzero input, at prefill *and* decode row counts, for bits
4, 5 and 6.** Note `VLLM_EXL3_B12X_ANY_BITS=1` newly routes **bits=4** matrices
too (K=10240→N=5120, i.e. the MTP module), not only the K5 MLP — worth knowing,
and they also agree.

### Hypothesis 3 (refuted): `prepare_weight` mutates the payload in place

If b12x's prepare repacked the trellis in place, every *other* consumer
(`ext.reconstruct`, the FP4/FP6 converters, the fp16 prefill cache) would read
repacked bytes afterwards — which would produce exactly this signature: plausible
garbage while each individual GEMM comparison passes. Tested with byte checksums
of `trellis`/`suh`/`svh` before and after prepare, plus `reconstruct` output
before vs after (`/tmp/mutprobe.py`):

| matrix | tensors mutated | reconstruct before vs after |
|---|---|---|
| K6 `down_proj` | **NONE** | cos 1.000000, max_rel 0.0000e+00 |
| K5 `gate_proj` | **NONE** | cos 1.000000, max_rel 0.0000e+00 |

Zero-copy as documented. Refuted.

### Where this leaves it

Refuted so far: (a) b12x's bits=5 kernel, (b) dtype mismatch, (c) in-place
mutation by prepare, (d) numerical disagreement anywhere in the served dispatch
at either row count, (e) prepared-weight cache aliasing (structural argument,
first pass). The corruption is therefore **not in the GEMM or its inputs** — it
is in something `_b12x_trellis_k6_supported() == True` changes *around* the
call. The strongest remaining candidate, unexercised by any test so far:

> **CUDA-graph buffer provenance.** The selftest runs eager, so it cannot see
> replay. `_b12x_trellis_linear` retains per-shape buffers for `m <= 128`, and
> `_warm_b12x_trellis_device` warms only the *first* shard per device
> (`_B12X_TRELLIS_WARMED_DEVICES` short-circuits), so most shapes first allocate
> lazily. Any shape whose buffers are first allocated *during* graph capture gets
> them from that graph's private pool. `ANY_BITS=1` adds bits=4/5 shapes to the
> set of graph-captured b12x callsites, so it enlarges exactly this exposure.
> Testing it means comparing eager vs replayed decode output for one captured
> batch size, which is a different instrument than the one built here.

That is the next thing to try, and it is now a *specific, falsifiable* claim
rather than the vague "merged-linear dispatch" lead from the first pass — which
this pass also weakened, since merged K5 shards agree numerically at both row
counts.

**Halting here per the objective's 6-attempt cap on one work item.** The flag
stays off, the warning stays in, and `VLLM_EXL3_B12X_SELFTEST=1` remains as
reusable verification for any future b12x work. The shipped fidelity profile is
unaffected: it runs K6-only b12x at PP 1630.0 ± 3.6 and KLD 0.003407.
