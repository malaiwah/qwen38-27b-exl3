# TG +32%: the MTP draft loop was running eager because the V1 runner has no speculator graphs

## The chain of reasoning (all measured)

1. `receipts/nsys-utilization-2026-08-19.md` showed a decode step doing **7.0 ms
   of GPU work in 344.8 ms of wall time (2% utilisation)**, so TG was host-bound.
2. Breaking that step down by NVTX scope gave the culprit precisely:

   | phase | ms per decode step |
   |---|---|
   | **`draft` (MTP)** | **40.7-42.6** |
   | preprocess | 2.6-2.7 |
   | forward (target verify) | 1.1-1.5 |
   | sample | 0.2 |
   | postprocess | 0.1 |

   The draft phase is **88% of the step**. (An earlier reading of "preprocess
   17.9 ms/call" was an artifact of one 299 ms first-call outlier; steady state
   is 2.6 ms.)
3. Only **11 `cudaGraphLaunch` calls** appeared in the whole trace for ~11
   decode steps, and their 1.45 ms average matches the *verify forward* — so the
   6-step draft loop was running fully eager.
4. `CUDAGRAPH_MODE=FULL` changed nothing (TG 143.1/71.0 vs 141.9/70.9), so it
   was not a graph-mode gate.
5. The log never printed `"Capturing model for speculator"` — **0 occurrences**.
   `MTPSpeculator` extends `AutoRegressiveSpeculator`, which *does* implement
   `init_cudagraph_manager` / `capture` / `run_fullgraph` with a
   `SpeculatorCudaGraphManager` for both prefill and decode. The capture call
   site is `vllm/v1/worker/gpu/model_runner.py:1069` — the **V2** runner. The V1
   runner (`vllm/v1/worker/gpu_model_runner.py`) contains **no**
   `speculator.capture` at all. We were on V1, so the graphs were never built.

## Two upstream bugs blocked the switch

`VLLM_USE_V2_MODEL_RUNNER=1` then failed, but not for the reason previously
recorded as a "V2-runner dead end":

1. First failure was **only KV sizing** — V2 leaves 9.35 GiB vs V1's 10.49 GiB,
   so 262,144 did not fit and it suggested 252,960. Not an incompatibility.
2. Then: `ValueError: num_speculative_tokens must be between 1 and 6, got 0`
   from `autoregressive/speculator.py:180`, followed by
   `RuntimeError: Scheduler selected an invalid speculative-token count 0`
   from `spec_decode/utils.py:37`.

**Both were triggered by our own scheduler optimisation** (upstream PR #438 /
#437): it sets `num_spec_tokens_to_schedule = 0` when every scheduled request
needs <=1 output token. The V1 runner tolerated 0; the V2 path raises in two
places. So two individually-correct features were mutually exclusive.

Fixes (7 lines each, mounted as `patches/autoregressive_speculator_patch.py`
and `patches/spec_decode_utils_patch.py`):

- `AutoRegressiveSpeculator.propose`: on `num_speculative_tokens == 0`, return
  `self.draft_tokens[:num_reqs, :0]` instead of raising. This mirrors the
  existing early-return at line 324.
- `limit_draft_tokens`: accept depth 0 and return `draft_tokens[:, :0]`. Note
  the function **already tolerated an empty draft** three lines below the guard
  (`if draft_tokens.shape[1] == 0: return draft_tokens`) — the range check
  simply ran first. So this is a guard-ordering bug, not a design change.

## Result (new default profile)

`VLLM_USE_V2_MODEL_RUNNER=1`, all-FP4, util 0.93, mnbt 3072, max-model-len
250,000. Verified with no env overrides at all:

| metric | V1 runner | **V2 + fixes** | north star |
|---|---|---|---|
| **TG essay** | 70.9 | **93.5-93.6** (+32%) | >= 83 **MET** |
| **TG fox** | 141.9 | **184.5-185.6** (+31%) | >= 190 (97.7%) |
| **PP** | 7627 | **7592-7697** | >= 7000 **MET** |
| context | 262,144 | 250,000 | >= 238,400 **MET** |
| vision + MTP | pass | pass | **MET** |
| MTP acceptance fox / essay | 0.97 / 0.32 | 0.93 / 0.30 | — |
| mixed stress gate | ROBUST | **ROBUST** | — |

Reproducibility: three consecutive TG runs gave fox 184.5 / 184.9 / 185.6 and
essay 93.5 / 93.6 / 93.6 — under 1% spread, so the gain is far outside noise.
GPU during stress: 31153 MiB, 2842 MHz, 389.8 W of a 600 W limit, 64 C.

Cost: 12,144 tokens of context (262,144 -> 250,000) for +32% TG. The V2 runner's
slightly larger fixed footprint is the reason; `receipts/memory-ledger.md` L12
records it.

## What this retires

The nsys receipt already de-prioritised b12x #234 (16-row skinny-M FP4 tile) on
the grounds that decode was 2% GPU-utilised. That reasoning stands, and this
change is the *correct* fix for the same symptom — it removes host overhead
rather than making idle GPU work cheaper. Draft-vocab pruning and an FP8 draft
head remain retired for the same reason.

Remaining unmet: KLD <= 0.012 and p99 <= 0.15, which
`receipts/kld-axis-conclusion-2026-08-19.md` proves require W4A8 (b12x #232),
and TG fox is 2.3% short of 190.
