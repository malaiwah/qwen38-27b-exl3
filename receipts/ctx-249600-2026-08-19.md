# throughput context 250,000 -> 249,600: a deterministic boot failure, caught by the user

**Date:** 2026-08-19 (late)

## What happened

After block 4, the systemd service (PROFILE=throughput default) entered a crash loop:

```
ValueError: To serve at least one request with the model's max seq len (250000),
9.26 GiB KV cache is needed, which is larger than the available KV cache memory
(9.25 GiB). ... the estimated maximum model length is 249696.
```

Deterministic — successive attempts (EngineCore pid=130, pid=131) failed identically,
so this is not profiling jitter. My own restart check tailed the FP4-conversion
progress lines and missed the ValueError below them; **the user caught it**. The
correct check is grep for the exception, not a tail — the block-boot helpers already
do this (`why()`), the manual restart did not.

## Root-cause status: bounded, not fully attributed

The deficit is ~10 MiB (0.01 GiB) at engine init. The last successful 250,000 boot
was the 600 W gate re-run; the failure window is everything landed since.

**Ruled out — warm-per-(device,bits)** (the K5-cure change): the warm callsite sits
behind `_b12x_trellis_k6_supported`, and with `ANY_BITS=0` (throughput default) only
`n_words == 96` shards pass -> exactly one plan warms, byte-for-byte the pre-cure
behaviour. Verified in source (`patches/vllm-exl3-multiprecision.py:3263-3279`,
`:1632-1646`).

**Prime suspect — GDN spec-row gate un-slicing** (`qwen_gdn_linear_attn_patch.py`,
port of upstream#51812): keeps gates un-sliced for speculative rows, which raises the
profile-run activation peak by an amount of the right magnitude (~10-20 MiB at
mnbt x hidden x 2B). Not re-verified by A/B boot because the patch fixes a LIVE
wrong-output bug under MTP+concurrency: **correctness keeps its 10 MiB; context
yields**. An A/B would only relitigate a patch we would keep at any answer.

## Fix

`MAX_MODEL_LEN` throughput default 250,000 -> **249,600** (below vLLM's own 249,696
estimate, 16-aligned, 0.16% loss). Criterion 5 needs >= 238,400 — unaffected.
Baseline `min_absolute` updated; README + model-card tables updated; the frontier
receipt keeps its 250,000 as a point-in-time record.

## Ledger

**L15**: ~10 MiB additional load/profile-time memory on all profiles since the GDN
spec-row correctness port (attribution: strong suspicion, not measured A/B — see
above for why we choose not to measure it). Visible only on throughput, whose
250,000-ctx margin was the thinnest; fidelity (238,400) and balanced (199,104)
absorb it silently.
