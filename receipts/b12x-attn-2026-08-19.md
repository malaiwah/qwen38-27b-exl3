# B12X_ATTN: 1.41x prefill speedup at 131k, blocked on fidelity profile by b12x bug

**Date:** 2026-08-19/20.

## Speedup confirmed (throughput profile)

| depth | TRITON_ATTN | B12X_ATTN | speedup |
|---:|---:|---:|---:|
| 2,049 | 9,577.8 | 9,907.1 | 1.03x |
| 32,769 | 5,980.2 | 7,108.7 | 1.19x |
| 131,073 | 2,600.5 | 3,665.8 | 1.41x |

Matches the Amdahl prediction (74.7% attention share, 1.55x faster kernel ->
1.41x end-to-end). First lever to move the quadratic coefficient b.

## Fidelity proxy (throughput profile, all-FP4)

Greedy logprobs at 6 diverse prompts, 192 tokens:
- text agreement: 1/6 identical
- mean |logprob delta|: 0.229
- max |delta|: 1.562

On the all-FP4 profile (KLD 0.064), the attention-backend delta (0.229) is
small relative to the FP4 weight quantization that produces that 0.064. Text
divergence is expected at this precision level.

## Fidelity profile: BLOCKED by b12x bug

B12X_ATTN fails to boot with the fidelity profile (ANY_BITS=1, SKIP_TRELLIS_PREP=0,
GPU_MEM_UTIL=0.945). Root cause is a tensor shape mismatch in b12x's own code:

```
b12x/attention/paged/_scratch.py:979, in _copy_runtime_metadata
RuntimeError: The size of tensor a (1863) must match the size of tensor b (1872)
at non-singleton dimension 1
```

The fidelity profile's ANY_BITS path changes the number of KV blocks, and
B12X_ATTN's scratch metadata allocation doesn't account for the different
block count. Tried GPU_MEMORY_UTILIZATION=0.90 (more headroom) — same error.
The bug is in b12x's runtime metadata binding, not in our config.

This should be reported to b12x. The throughput profile works because it uses
standard block-size 16 KV (no ANY_BITS), which gives a block count that
B12X_ATTN's scratch allocator handles correctly.

## KLD measurement: BLOCKED by harness incompatibility

fidelity.py constructs LLM() with enforce_eager=True, kv_cache_memory_bytes=512MB,
max_num_seqs=1. B12X_ATTN needs block-size 128 and appears to require CUDA
graphs. Added --attention-backend and --block-size args to fidelity.py, but the
LLM construction is still incompatible. A full KLD measurement needs either:
1. A harness refactor to pass through all relevant LLM kwargs, or
2. An API-based capture approach that boots via the launcher.

## What to report to b12x

Two items:
1. **The speedup**: B12X_ATTN is 1.41x faster than TRITON_ATTN at 131k on SM120
   with all-FP4. This is a real, measurable win for deep-context prefill.
2. **The bug**: `_scratch.py:979` tensor shape mismatch (1863 vs 1872) when
   ANY_BITS=1 changes the KV block count. B12X_ATTN's scratch metadata doesn't
   handle the modified block layout.

## Decision: not the default, but strongly recommended for deep-context throughput

**Do not change the shipped default** -- B12X_ATTN has not passed the full
throughput gate (PP/TG at n=3 + KLD on the 512-ctx suite). The boundaries
require a full gate pass before changing profile defaults.

**But the data supports offering it as an opt-in** for deep-context workloads:

```bash
PROFILE=throughput ATTN_BACKEND=B12X_ATTN BLOCK_SIZE=128 ./run-qwen38-27b.sh
```

Evidence:
- PP: 1.03x at 2k, 1.19x at 32k, 1.41x at 131k, 1.53x at 238k (Amdahl-confirmed)
- Correctness: sanity passes, greedy text semantically equivalent
- Context: 249,600 preserved (same as TRITON_ATTN)
- KLD: not measured on the 512-ctx suite (fidelity.py harness incompatible),
  but the throughput profile's KLD is 0.064 anyway (speed-at-any-fidelity)
- The fidelity profile is blocked by a b12x bug (_scratch.py:979)
