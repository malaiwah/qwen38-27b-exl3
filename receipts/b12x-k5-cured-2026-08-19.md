**Date:** 2026-08-19 (late)
**Supersedes:** `receipts/b12x-k5-parked-2026-08-19.md` (parked at the 6-attempt cap)

## The fix: six lines, and it came from the GLM cross-model exercise

`_warm_b12x_trellis_device` keyed its "already warmed" set on **device index
alone**. B12X initialises a **separate mixed-Trellis plan per bit width**, so with
`ANY_BITS=1` the bits=4 and bits=5 plans were never warmed — they initialised
lazily on their first real call. Decode is CUDA-graph captured, so that first call
landed **inside capture** and their internal buffers came from that graph's
private memory pool. Result: plausible-shaped garbage on replay while every
eager-mode comparison passed.

Keying the warm on `(device, bits)` fixes it:

```python
bits = int(trellis.shape[2]) // 16
key = (device_index, bits)
if key in _B12X_TRELLIS_WARMED_DEVICES:
    return
```

**Provenance of the hypothesis.** Writing up what transfers to GLM-5.2
(`receipts/glm52-transfer-2026-08-19.md`) required reading how r34 handles graph
capture on the MoE path — and it pre-initialises scratch for *every* codebook tier
before capture. That is the same doctrine as fork PR #314's autotune priming. Both
pointed at the same gap in our warm. The parked receipt's first-pass lead
(merged-linear dispatch) was wrong; the second-pass lead (graph-pool provenance)
was right. **The cross-model write-up paid for itself here.**

1. **"The trellis path tops out at 2,457.7 tok/s"** (frontier receipt). That number

   M-dispatch existed. The trellis-exact path now **measures 2,987.7 in
   production**, above the old "ceiling". Criterion 1 would need **234%** of that —
